# دورة تطوير ونشر السكربتات

هذا الملف هو المرجع الرسمي لإدارة إصدارات سكربتات **سكربتات تفيد المعلم**.

## الفروع

- `main`: النسخ المستقرة فقط.
- `dev`: تجميع التطوير قبل النشر.
- `feature/<script>-<feature>`: ميزة جديدة كبيرة عند الحاجة.
- `fix/<script>-<bug>`: إصلاح معزول عند الحاجة.

## قبل أي تعديل

1. ابدأ من `dev` أو فرع مشتق منه.
2. لا تعدّل النسخة المنشورة مباشرة في GreasyFork ثم تنسى GitHub.
3. GitHub هو المصدر الرئيسي للكود بعد اكتمال ترحيل السكربت.
4. إذا وصل سكربت قديم بدون حقوق أو بروابط ناقصة، تُدمج فيه هوية المطور الرسمية من `config/author.json` قبل اعتماده.
5. لا يُقبل أي اختلاف يدوي في اسم المطور أو روابطه أو صيغة الحقوق بين السكربتات.

## الهوية والحقوق الإلزامية

كل سكربت حالي أو مستقبلي يجب أن يحمل الهوية الموحدة للمطور، ويشمل ذلك على الأقل:

- `@namespace`
- `@author`
- `@homepageURL`
- `@supportURL`
- `@copyright`
- `@license`
- كتلة حقوق داخل المصدر تتضمن GreasyFork وGitHub وX وSnapchat وعبارة الحقوق.

المرجع الوحيد لهذه البيانات هو `config/author.json`، ويجب ألا تُنسخ قيم مختلفة يدويًا إلى أي سكربت.

## أرقام الإصدارات

نتبع Semantic Versioning:

- `PATCH`: إصلاح خطأ بدون تغيير الوظيفة الأساسية، مثال `1.4.0 → 1.4.1`.
- `MINOR`: إضافة ميزة متوافقة، مثال `1.4.1 → 1.5.0`.
- `MAJOR`: تغيير كبير أو غير متوافق، مثال `1.5.0 → 2.0.0`.

يجب تحديث رقم الإصدار في كل المواقع التالية:

1. `@version` داخل Header.
2. أي ثابت إصدار داخلي مثل `APP.version` أو `VERSION` إن وجد.
3. `scripts/catalog.json`.
4. `CHANGELOG.md` الخاص بالسكربت.

## سجل التغييرات إلزامي

لا يتم نشر إصدار جديد بدون كتابة فرق واضح عن الإصدار السابق. يجب أن يوضح `CHANGELOG.md`، حسب ما ينطبق:

- **Added — جديد:** الميزات الجديدة.
- **Improved — تحسين:** تحسينات الأداء أو الواجهة أو سهولة الاستخدام.
- **Fixed — إصلاح:** الأخطاء التي تم إصلاحها.
- **Changed — تغيير:** أي تغيير في السلوك أو طريقة الاستخدام.
- **Removed — إزالة:** ما تم حذفه أو إيقافه.
- **Compatibility — توافق:** تغييرات المواقع المستهدفة أو المتصفح أو Tampermonkey.

لا نستخدم عبارات عامة مثل «تحسينات متنوعة» إذا كانت هناك تغييرات يمكن شرحها للمستخدم بوضوح.

## تحديث معلومات GreasyFork مع كل إصدار

كل نشر على GreasyFork هو **إصدار منتج** وليس مجرد رفع ملف جديد. لذلك قبل النشر يجب مراجعة وتحديث المعلومات التي يراها المستخدم بحيث تتوافق مع النسخة الحديثة.

لكل إصدار نراجع:

1. **وصف السكربت**: هل ما زال يصف الوظائف الحالية بدقة؟
2. **What's new / سجل التغييرات**: ملخص واضح لما تغير منذ الإصدار السابق.
3. **تعليمات الاستخدام**: تحديثها إذا تغيّرت الأزرار أو الخطوات أو طريقة التشغيل.
4. **الميزات**: إضافة الميزات الجديدة وإزالة أي وصف لميزة لم تعد موجودة.
5. **التوافق**: تحديث المواقع أو الصفحات المدعومة عند تغير `@match`.
6. **الصور/اللقطات**: تحديثها إذا تغيرت الواجهة بشكل واضح.
7. **روابط الدعم والمصدر**: يجب أن تبقى مطابقة للهوية الرسمية.
8. **رقم الإصدار**: التأكد أنه مطابق لـ GitHub وTampermonkey.

إذا كان الإصدار إصلاحًا داخليًا صغيرًا ولا يغيّر الوصف العام، يبقى الوصف كما هو، لكن **سجل ما الجديد يجب أن يوضح الإصلاح**.

## الاختبار

قبل الدمج إلى `main`:

- تشغيل السكربت على الصفحة المستهدفة فعليًا.
- اختبار الوظائف الأساسية والوظائف التي تم تعديلها.
- التأكد من عدم ظهور أخطاء JavaScript جديدة في Console.
- التأكد من أن التخزين المحلي والإعدادات السابقة لم تتضرر.
- تشغيل فحص GitHub Actions بنجاح.
- مراجعة الهوية والحقوق والروابط الموحدة.
- مراجعة نص التحديث الذي سيظهر للمستخدم على GreasyFork.

## الدمج والنشر

1. فتح Pull Request من `dev` إلى `main`.
2. مراجعة التغييرات (`Files changed`).
3. انتظار نجاح فحص `Validate Userscripts`.
4. التأكد من اكتمال `CHANGELOG.md` وملخص GreasyFork للإصدار.
5. دمج PR.
6. مزامنة GreasyFork من GitHub أو تحديثه بالطريقة المعتمدة.
7. تحديث معلومات صفحة GreasyFork عند الحاجة: الوصف، الاستخدام، الميزات، الصور، التوافق.
8. نشر ملخص «ما الجديد» للمستخدمين.
9. اختبار التحديث من Tampermonkey بعد النشر.
10. التأكد أن النسخة المثبتة تعرض نفس رقم الإصدار الموجود على `main`.

## قاعدة ذهبية

**لا يوجد إصدار منشور غير موجود على `main`، ولا يوجد تعديل مباشر في GreasyFork لا يعود إلى GitHub، ولا يوجد إصدار جديد بدون شرح واضح للمستخدم عما تغير.**

## طوارئ إصدار مكسور

إذا نُشر إصدار به مشكلة:

1. لا نحذف تاريخ Git.
2. ننشئ إصلاح PATCH جديدًا.
3. إذا كان الإصلاح يحتاج وقتًا، يمكن الرجوع للكود السابق مع إصدار PATCH أعلى.
4. نسجل سبب المشكلة والإصلاح في `CHANGELOG.md`.
5. نحدّث ملاحظة الإصدار في GreasyFork بوضوح حتى يعرف المستخدم ما تم إصلاحه.
